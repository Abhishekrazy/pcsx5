# AUDIT 2026-09-07 - Guest pixel shader 0x215795900 versus its generated SPIR-V

Read-only audit. No production code was changed. The question is whether the
generated SPIR-V faithfully implements the guest bytecode for the one pass that
introduces both title-screen artifacts.

| | |
|---|---|

| Version | 1.5 |

| Capabilities | Shader, Int64, ImageQuery |

| `spirv-val --target-env vulkan1.2` | **VALID** |

The module is a register-machine emulation: it declares `sgpr` and `vgpr`
arrays of 256 uints and simulates the GCN register file, which is why access
chains and loads dominate its instruction count. Structural validity is
evidence the module is well-formed; it is not evidence of semantic
equivalence, and is not treated as such below.

## 4. Guest shader semantics

Data flow, read out of the listing:

```
2 interpolated attributes (VInterpP1/P2 x4)  ->  v0, v1  (screen UV)
18 uniform constants (SBufferLoadDwordx2 + Dwordx16)
        |
        v
~220 instructions of arithmetic: 82 multiplies, 43 fused multiply-adds,
35 adds, 16 subtracts, 4 reciprocals, and 40 trig evaluations
(33 cosines, 7 sines)
        |
        v
one displaced coordinate pair in v4, v5
        |
        v
ImageSample @0x047C  -  vaddr v4, srsrc s[0], ssamp s[8], dmask 0xF
        |
        v
2 x VCvtPkrtzF16F32  (pack to half pairs)
        |
        v
Exp @0x04AC  (compressed export to MRT0)  ->  SEndpgm
```

**This is a single-tap UV displacement shader.** It samples its source exactly
once, at a coordinate computed by a trig-heavy procedural function of the
interpolated UV and eighteen constants.

one-to-one, `OpFMul`, is explained precisely by the 40 turns-to-radians
conversions the trig lowering requires (33 + 7 = 40; 82 + 40 = 122).

## 6. Texture and sampler behaviour

Guest: `ImageSample F0800F08 00400004` - address register v4 (so the coordinate
pair is v4, v5), resource `s[0]`, sampler `s[8]`, `dmask 0xF`, implicit LOD, 2D
non-arrayed.

Generated: loads `vgpr[4]` and `vgpr[5]`, bitcasts each to float, builds a
`v2float`, and issues `OpImageSampleImplicitLod` with all four components
extracted back into the register file.

Coordinate source, component count, sample kind and LOD behaviour all match.
`VERIFIED`.

## 7. Coordinate transformation analysis

The coordinate path is: interpolated UV -> ~220 arithmetic instructions
dominated by sines and cosines -> one displaced coordinate -> one sample.

The shader does **not**:

- sample the source more than once
- combine multiple taps
- mirror or repeat coordinates explicitly
- use derivatives beyond the implicit LOD of a single sample
- branch on data (10 basic blocks, no data-dependent texture reads)

## 8. Logo doubling

**The multi-sample explanation is FALSIFIED.** The shader takes exactly one
tap. Doubling cannot come from combining displaced samples here, because there
is only one sample.

What remains is that a large-amplitude coordinate displacement can map two
separated screen regions onto overlapping parts of the source, which reads as a
doubled or melted glyph from a single tap. With 40 trig evaluations driving the
displacement, that is exactly the shape of function this shader computes.

The translation of every operation feeding that displacement matches the guest
one-for-one, including the turns-to-radians convention that would have been the
obvious way to get a wildly wrong warp.

## 9. Intermittent block artifacts

Candidate mechanisms inside this shader, and what the audit found:

- **Uninitialised registers** - not established; the register file is
  zero-initialised and the listing has no read-before-write that was identified.
- **Out-of-range coordinates** - plausible. A large displacement can push the
  sample outside `[0,1]`, where the result depends on the sampler's addressing
  mode. The addressing mode itself was not audited here.
- **Half-precision packing** - `VCvtPkrtzF16F32` is round-toward-zero to half;
  `PackHalf2x16` is round-to-nearest-even. A rounding-mode difference exists,
  though it affects the last bits of the output colour, not block structure.
- **Approximate reciprocal** - a precision difference in our favour.
- **NaN or infinity** - not investigated.

**Status unchanged: observed, not causally attributed.** Nothing in the
comparison explains a blocky, intermittent artifact.

## 10. Translator paths implicated

None conclusively. Two nuances worth recording, neither demonstrated to affect
the artifacts:

1. `VRcpF32` lowers to an exact `OpFDiv` where hardware is approximate.
2. `VCvtPkrtzF16F32` specifies round-toward-zero; `PackHalf2x16` rounds to
   nearest-even.

Both are candidate discrepancies in the sense the brief defines, not confirmed
root causes.

## 11. Decision

**Case A - semantic equivalence established** for the operations relevant to
both artifacts. Every arithmetic class matches exactly in count and meaning,
the single texture sample matches in coordinate source and sampling mode, and
the one apparent mismatch is fully explained by a required and correctly
implemented convention conversion.

The translator should **not** be modified on this evidence.

## 12. Remaining unknowns

- Whether the warp this shader computes is the game's intended appearance. The
  audit makes the shader's *intent* clear - a procedural single-tap
  displacement - but without a reference capture, intent is not correctness.
- The cause of the intermittent blocks.
- The sampler addressing mode used for out-of-range coordinates, which was not
  audited and is the most plausible remaining candidate for the blocks.
- Whether the two rounding nuances above have any visible effect.

## 14. Next boundary

The shader is faithfully translated, so the next question is **runtime state
rather than translation**: what the eighteen constants feeding the displacement
actually contain, and what sampler state the single sample uses.

Concretely, and in this order:

1. Dump the 18 uniform constants this pass loads and check they are plausible
   (finite, stable frame to frame, varying with time as an animated warp
   requires). A wrong constant produces a wrong warp with a perfectly correct
   shader.
2. Audit the sampler's addressing mode against the guest sampler descriptor,
   since out-of-range coordinates are the leading remaining candidate for the
   blocks.

Both are read-only and neither requires a reference capture.
